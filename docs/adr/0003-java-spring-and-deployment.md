## Đề xuất kiến trúc Tech để review

1. Một repo, hai ứng dụng: `apps/web` chỉ có giao diện, `apps/api` là Java API sở hữu auth, quyền, quy tắc tài chính và persistence. Caddy cung cấp một origin; `/api/*` giữ nguyên prefix tới Spring MVC, URL khác phục vụ React static với SPA fallback. Không có API Node/Hono trong đường chạy mới. Browser không kết nối trực tiếp DB/Redis/SMTP. FE không chứa bí mật hoặc kiểm quyền quyết định. OpenAPI là hợp đồng HTTP; TypeScript client nếu sinh từ OpenAPI là quyết định ticket sau, không đưa logic Java vào browser.
2. Dev/test dùng Compose với Caddy, web static/preview, Java API, PostgreSQL, Redis và Mailpit; chỉ Caddy bind loopback host. Cô lập DB, secret, volume và project name giữa dev/test. Production cài Caddy, file web tĩnh, Temurin 25 + JAR qua `systemd` và PostgreSQL trực tiếp trên Ubuntu VPS. **Tech đề xuất** cài Redis trên cùng VPS cho bộ đếm; TS34 chỉ chốt Redis là dịch vụ riêng, chưa chốt máy chạy. Chỉ 80/443 public, API/DB/Redis chỉ nghe loopback hoặc Unix socket nếu chọn cùng VPS. SMTP thật ở ngoài VPS khi Ninh chọn nhà cung cấp. Caddy nhận HTTPS ở production, không tự khẳng định TLS khi chưa có domain/DNS.
3. Spring MVC áp dụng `/api` và trả JSON lỗi có mã ổn định, không lộ stack trace, token, secret hoặc thông tin định danh khác người dùng. DTO validation ở HTTP boundary; Spring Security kiểm quyền từng endpoint và truy vấn luôn giới hạn `owner_id` từ principal đã xác thực. JPA entity không được xuất thẳng ra HTTP. Liquibase giữ một chuỗi migration có version; production không dùng `ddl-auto` để sửa schema. DB là nguồn sự thật cho tài chính và trạng thái phiên; Redis chỉ chứa bộ đếm throttle.
4. Caddy→Spring dùng hợp đồng peer/header/secret ở phần dưới; không tin forwarded header của client hoặc `getRemoteAddr()` sau khi một filter đã viết lại. Mọi request đổi trạng thái, kể cả login, setup, refresh và logout, kiểm `Origin` đúng origin đã cấu hình và CSRF token theo luồng SPA bên dưới; cookie `SameSite=Lax` là hàng rào bổ sung. CORS không mở origin khác. Cần thử browser thật, Origin/CSRF thiếu hoặc sai và direct API trước gate.
5. Spring Security xác minh chữ ký, `iss`, `aud`, `exp`, `nbf`, `jti`, loại token và thuật toán cố định; khóa ký chỉ ở server, có `kid` để luân chuyển. Tech đề xuất access JWT 15 phút và refresh JWT 7 ngày trong hai cookie `HttpOnly`/`Secure`, host-only; không lưu trong `localStorage`. Access cookie dùng `Path=/api`; refresh cookie dùng `Path=/api/auth`, để cả `/api/auth/refresh` và `/api/auth/logout` nhận được refresh token. Logout xác minh refresh token còn hợp lệ **hoặc** access JWT còn hợp lệ, rồi thu hồi **mọi** family quản lý theo CM01-Q2/B; nếu token đã hết hạn nhưng cookie còn hiện diện, API vẫn phải xác định chủ tài khoản an toàn trước khi báo đăng xuất toàn bộ, hoặc báo cần đăng nhập lại mà không khẳng định thu hồi. Xóa cả hai cookie bằng `Set-Cookie` đúng tên/path dù DB lỗi, nhưng khi DB lỗi phải báo trạng thái thu hồi chưa rõ và các request sau fail closed. Không dùng tiền tố `__Host-` cho cookie `Path` hẹp vì tiền tố đó yêu cầu `Path=/`; nếu chọn `__Host-`, đổi cả hai cookie sang `Path=/` và review phạm vi gửi cookie. Tên cookie dev HTTP khác, cấu hình production từ chối cookie không Secure. [Spring Security có hỗ trợ giải mã/kiểm JWT, nhưng bearer filter mặc định đọc `Authorization` header](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html); đọc token từ cookie và trạng thái DB là tích hợp riêng phải kiểm thử, không tự có sẵn từ starter.
6. Để đạt **thu hồi ngay** theo TS33, mỗi request được bảo vệ phải kiểm trạng thái phiên/tài khoản trong PostgreSQL sau khi kiểm JWT; không cache trạng thái cho phép ở Redis hay trong tiến trình. Đề xuất lưu `jti`/family, subject, thời hạn, trạng thái thu hồi và hash refresh token trong DB, không lưu JWT nguyên văn. Refresh dùng transaction/CAS một lần như phần dưới; chính sách xử lý reuse chưa chốt vì không thể luôn phân biệt retry hợp lệ với kẻ dùng lại token. Đăng xuất, đổi mật khẩu và xóa tài khoản thu hồi trạng thái DB trong transaction; các request sau commit bị từ chối. Nếu DB không kiểm được thì fail closed, kể cả JWT còn hạn. Cơ chế khóa ký/luân chuyển, TTL record và hành vi nhiều thiết bị cần Tech/BA/PM rà tại CM-01/#04; đây là **đề xuất**, không phải câu trả lời Ninh đã chốt.
7. Redis + Lettuce giữ bộ đếm thử login/setup theo cửa sổ giới hạn được PM/BA duyệt lại, với thao tác tăng/kiểm nguyên tử và TTL. Redis lỗi làm **thao tác xác thực/thiết lập mới** fail closed trước kiểm mật khẩu hoặc gửi link; request đã có phiên hợp lệ vẫn dựa vào DB/quyền, không phụ thuộc Redis. Nếu Redis lỗi nhưng API health báo healthy thì phải có chỉ báo degraded riêng; health/readiness và phục hồi sau Redis/DB restart cần thử. Quota/IP cụ thể ở thiết kế CM-01 Node là lịch sử, không tự áp dụng cho 10 người dùng sau #04.
8. Nghiệp vụ tiền VND dùng số nguyên, không `float`/`double`. Đề xuất `@Transactional` cho mỗi thay đổi ví/giao dịch; kiểm `owner_id`, bản ghi/version cũ, khóa ví liên quan theo thứ tự cố định hoặc optimistic version kèm retry có giới hạn, bảo toàn cập nhật đồng thời. Idempotency key cho POST ghi tiền, lưu kết quả trong cùng transaction với thay đổi dữ liệu, để retry khi phản hồi chưa rõ không ghi trùng; trạng thái kết quả chưa rõ phải được truy vấn lại theo yêu cầu R64/F25. Sửa/xóa/khôi phục dùng version precondition để báo xung đột theo B18/B30, không ghi đè. Thiết kế chính xác về lock, unique constraint và quy tắc ví vẫn là `STORY_TECH_GAP` từng module, không được coi đã giải quyết ở ADR này.
9. SMTP qua Spring Mail với timeout hữu hạn; Mailpit là hộp thử. Gửi mail không chung transaction DB: CM-01 phải giữ generation/CAS, liên kết một lần và trạng thái kết quả chưa rõ theo sản phẩm; cần thiết kế lại bằng JPA/Liquibase, kiểm nhiều tiến trình Java và Mailpit. Không tạo HTTP endpoint bootstrap quản lý; lệnh vận hành nội bộ có quyền tối thiểu. Email/SMTP production, domain, VPS, tài khoản hệ thống và secret thực chưa có.

### Hợp đồng CSRF SPA đề xuất

- `GET /api/auth/csrf` là endpoint công khai, chỉ cấp CSRF token, không tạo tài khoản/phiên hay đổi dữ liệu sản phẩm; `Cache-Control: no-store`. Controller buộc đọc `CsrfToken` để vật chất hóa token bị deferred. Dùng `CookieCsrfTokenRepository` với cookie host-only, `Path=/`, `SameSite=Lax`, `Secure` ở production và **JS đọc được**, cộng handler SPA của Spring Security (`csrf.spa()` ở dòng tương thích sau khi build xác minh) để nhận raw token từ `X-XSRF-TOKEN` và xử lý BREACH/deferred token. JWT vẫn chỉ nằm trong cookie `HttpOnly`. Cần kiểm cấu hình cookie/handler trên bản Spring Boot 4.1 cụ thể; [Spring Security mô tả riêng vấn đề SPA, deferred token và token bị xóa sau auth/logout](https://docs.spring.io/spring-security/reference/7.0/servlet/exploits/csrf.html).
- Trình duyệt mới mở trang thiết lập/đăng nhập gọi GET trên cùng origin, đọc CSRF cookie, gửi `X-XSRF-TOKEN` cùng `Origin` chính xác trên POST setup/login. Mọi POST/PUT/PATCH/DELETE, kể cả refresh/logout, đều qua hai phép kiểm trước đổi trạng thái. GET setup link chỉ hiển thị form, không tiêu thụ link. Từ chối request thiếu/sai token/Origin bằng 403, không ghi DB/đổi cookie auth; GET CSRF không được trả CORS cho origin ngoài.
- Sau **setup hoặc login thành công**, Spring Security có thể xóa CSRF cookie qua auth strategy; sau **logout** logout handler cũng xóa nó. API/FE buộc GET `/api/auth/csrf` lần nữa trước POST kế tiếp; không giả định token cũ còn dùng được. Sau **refresh** do endpoint JWT tự quản lý, Tech đề xuất chủ động rotate CSRF cookie và FE cũng GET token mới trước POST kế tiếp; lỗi 403 do CSRF cũ được phép GET lại rồi retry **chỉ khi server đã chắc chắn chưa đổi trạng thái**. Network timeout/response mất không được retry mù một POST tài chính hoặc refresh. Test anonymous→login/setup→refresh→logout→anonymous trên browser thật, kể cả reload/deep link/hai tab và cookie Secure production.

### Refresh rotation và kết quả chưa rõ

- `POST /api/auth/refresh` đòi refresh JWT cookie, Origin và CSRF. Trong PostgreSQL transaction, khóa một dòng family, xác minh hash/`jti`, thời hạn, trạng thái tài khoản và `current_jti`; chỉ current token được CAS sang `used` và tạo next `jti`/hash một lần. Commit trước khi gửi `Set-Cookie`; hai request đồng thời thì đúng một request thắng, request thua **không nhận JWT mới**. Ràng buộc unique/CAS và DB time cần thử với hai tiến trình Java. Access JWT mới chỉ được chấp nhận khi family/`jti` trong DB còn hiệu lực.
- Nếu commit xong nhưng response hoặc `Set-Cookie` mất, browser còn refresh cũ: client phải hiển thị **kết quả chưa rõ**, không tự báo đã duy trì đăng nhập. Nó có thể GET trạng thái bằng access JWT còn hạn; nếu access hết hạn/không xác minh được thì yêu cầu đăng nhập lại. Không tái phát JWT từ refresh cũ và không lưu JWT plaintext để replay response. FE single-flight trong một tab chỉ giảm duplicate; hai tab hoặc retry mạng vẫn phải xử lý ở BE.
- **Ninh đã xác nhận CM01-Q3/A ngày 14/10/2026:** Khi refresh cũ xuất hiện lại sau lần dùng đầu mà không thể chứng minh là retry hợp lệ, thu hồi ngay family của phiên đó và yêu cầu đăng nhập lại. Hai tab hoặc response mất có thể gây đăng xuất oan; UI phải báo cần đăng nhập lại, không tự khẳng định tiếp tục phiên. Việc chủ động bấm đăng xuất lại theo CM01-Q2/B thu hồi **mọi** phiên quản lý trên mọi điện thoại. Tech phải chứng minh hai phạm vi thu hồi này không bị trộn. [Q&A CM-01](../../.scratch/capmoney-manager-setup/qna.md).

### Hợp đồng nguồn IP Caddy→Spring đề xuất

- Caddy là ingress duy nhất, không có CDN/proxy trước Caddy trong bản đầu. `reverse_proxy` **ghi đè** `X-Forwarded-For` và `X-Real-IP` bằng đúng một `{remote_host}` lấy từ TCP peer của Caddy; bỏ header `Forwarded` và `X-Forwarded-Host` từ client, đặt `X-Forwarded-Proto` theo scheme Caddy. Caddy cũng ghi đè `X-CM-Edge-Auth` bằng secret ngẫu nhiên riêng giữa edge và API; không để client cung cấp giá trị này. Secret chỉ trong file quyền hạn chế/Compose secret, không in qua log/config dump. [Caddy hỗ trợ `header_up`, `{remote_host}` và runtime file placeholder](https://caddyserver.com/docs/caddyfile/concepts); cú pháp thực tế phải qua `caddy adapt` và probe test, không xem đoạn này là cấu hình đã chạy.
- Spring đặt `server.forward-headers-strategy=none`, không bật Tomcat `RemoteIpValve` hay `ForwardedHeaderFilter` viết lại remote address. Filter ingress chạy trước auth/throttle, đọc TCP peer **thật** qua `HttpServletRequest.getRemoteAddr()` ở cấu hình này, rồi so secret edge bằng phép so hằng thời gian. Chỉ khi peer thuộc đường Caddy đã định và secret đúng mới nhận IP từ hai header; cả hai phải hiện diện, mỗi header đúng **một** IP hợp lệ, không có comma/multiple value, bằng nhau. Thiếu/sai peer/secret/header/IP thì từ chối request nhạy cảm trước throttle/auth; không fallback sang IP do client nhập. Không lấy IP từ `Host`/`X-Forwarded-Host`. [Spring Boot có cấu hình forwarded-header strategy](https://docs.spring.io/spring-boot/appendix/application-properties/index.html).
- **Compose dev/test:** API chỉ nối `api_net` riêng với Caddy và không publish host port; peer phải thuộc subnet `api_net` đã định trong cấu hình dev/test **và** secret hợp lệ. Không pin địa chỉ container Caddy động; recreate Caddy vẫn hoạt động với secret/subnet ổn định. **VPS direct install:** API chỉ bind `127.0.0.1` (hoặc Unix socket được thiết kế/review riêng); peer phải là loopback **và** secret hợp lệ, trong khi firewall chỉ public 80/443. Process khác trên VPS gọi thẳng API không có secret bị chặn. Đổi proxy/network/secret phải review và test lại; không coi subnet/loopback tự nó chứng minh danh tính Caddy. Cần test direct API, spoof/multiple/malformed XFF/X-Real-IP, secret sai/thiếu, Caddy restart/recreate và lỗi DNS/network. Không báo IP trust đã được chứng minh trước test Java thực.

## Checklist gate của bản thiết kế gốc

- **Tech review độc lập:** kiểm ranh giới Caddy→Spring, Origin/CSRF/cookie, JWT DB revocation và refresh race/reuse, Redis fail closed, JPA transaction/idempotency, Liquibase migration, Mailpit/SMTP unknown, direct VPS/systemd và phiên bản dependency. PM đối chiếu TS10–TS38, phạm vi INFRA-01/CM-01 và rủi ro TS26. BA cập nhật spec 20 mục/AC của hai Story trước khi cấp lại `BA_READY`.
- **INFRA-01/#47:** thiết kế/QA case Compose Java+Redis mới; build Maven Java 25, route SPA/API, DB/Redis/Mailpit health và outage recovery, network/secret/volume, lỗi Origin/IP/CSRF bằng probe test-only. Kết quả Node/Hono IF-T03 fail không được chuyển thành pass. Reviewer code và QA độc lập chạy trên commit xác định.
- **CM-01/#43–#45:** cập nhật hợp đồng setup/login/JWT/refresh/logout, DB state, Redis throttle, email generation/CAS và OpenAPI; chạy Testcontainers PostgreSQL/Redis, concurrent setup/refresh/revocation, browser cookie/CSRF; Mailpit trước, SMTP thật khi có hạ tầng. Chỉ sau gate mới giao Dev.
- **CI/production:** GitHub Actions chạy Maven unit/integration, FE build và Playwright theo ticket; test thật iPhone/Android khi gate sản phẩm cần. VPS direct install cần runbook có quyền file/secret, migration và rollback được thử trước khi mở thật. Không có bằng chứng deploy hay backup hiện nay; volume riêng **không phải bản sao lưu**. Ninh đã chấp nhận rủi ro mất dữ liệu do hỏng VPS/volume, nhưng PM phải nhắc lại trước vận hành thật.

## Điểm chưa rõ / không tự quyết định thay Ninh

- VPS, DNS/domain, SMTP thật, thời điểm phát hành, quyền vận hành và bản vá chính xác chưa chốt. Production install là thiết kế mục tiêu, chưa được triển khai.
- CM01-Q2/B đã chốt đăng xuất mọi điện thoại; CM01-Q3/A đã chốt thu hồi family khi refresh reuse không phân biệt được retry/replay. Cách phát lỗi và test nhiều tab vẫn phải vào thiết kế CM-01; mức quota Redis và việc login bị chặn khi Redis lỗi cần BA/PM rà tác động sản phẩm.
- Không tự cấp gate hoặc tạo ticket mới từ ADR đề xuất. Chỉ reviewer Tech/PM theo [workflow](../workflows/capmm-end-to-end.md) mới xác nhận bản thiết kế đủ làm nguồn triển khai.
